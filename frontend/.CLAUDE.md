# CLAUDE.md — Kuntur (Frontend)

## Descripción

Kuntur es un SaaS de gestión educativa para colegios y nidos de **inicial y primaria en Perú**. Este documento cubre el frontend: la aplicación web que consumen Dirección, Docente y Familia, conectada al backend real (NestJS + PostgreSQL).

## Alcance

Tres roles con vistas y permisos distintos, dentro de la misma aplicación:

- **Dirección** — control total del colegio: alumnos, docentes, aulas, panorama general, alertas.
- **Docente** — acotado a su(s) aula(s): asistencia, ficha del alumno, cuaderno de control, comunicados de su aula.
- **Familia** — vista de solo lectura de su(s) hijo(s): asistencia, comunicados, autorizaciones, portafolio, resúmenes.

Pantallas/módulos centrales:

- Login con autenticación real contra el backend (JWT).
- Asistencia diaria con histórico.
- Ficha del alumno: observaciones y conclusiones descriptivas generadas por IA.
- Cuaderno de control: comunicados de aula/individuales, autorizaciones con flujo de aprobación y firma.
- Registro por voz (dictado) en ficha, cuaderno y asistencia, con borrador editable y confirmación explícita antes de guardar.
- Perfil de avance del alumno.
- Notificaciones push.

**Etapa actual:** existe una demo funcional en React (Vite, single file, datos en memoria, sin backend). El frontend real evoluciona esa demo o la reconstruye para conectarse al backend en producción, manteniendo la identidad visual "cuaderno" ya validada (papel, rayas, Fredoka + Inter, amarillo Kuntur).

## Contrato de modelo de dominio

`CONTRACT.md` es el contrato técnico compartido entre backend y frontend: define cada entidad del sistema (campos, tipos, relaciones) y los enums válidos, en formato estandarizado. Los tipos de TypeScript del frontend (props, respuestas de API, formularios) deben derivarse de ese documento — si el frontend necesita un dato que no está ahí, se agrega al contrato primero, no se inventa un campo local. El catálogo de módulos activables por colegio vive aparte, en `MODULES.md`. Ambos archivos están en la raíz del proyecto, junto a este `CLAUDE.md`.

## Stack

| Capa                           | Elección                                                                          |
| ------------------------------ | --------------------------------------------------------------------------------- |
| Framework                      | React + Vite                                                                      |
| Lenguaje                       | TypeScript                                                                        |
| Cliente HTTP / estado servidor | Por definir (ej. TanStack Query)                                                  |
| Estilos                        | Por definir (la demo actual usa CSS con estética "cuaderno" propia)               |
| Auth                           | JWT emitido por el backend (Nest), manejo de sesión y refresh token en el cliente |
| Notificaciones                 | Push notifications (Web Push / equivalente)                                       |
| Hosting                        | Vercel                                                                            |

## Convenciones de nomenclatura

- **Todo el código se escribe en inglés**: nombres de componentes, variables, funciones, props, hooks, archivos, carpetas, comentarios en código.
- **Todo lo que ve el usuario final está en español**: textos de UI, labels, mensajes de error, contenido de notificaciones, copy en general.
- Al consumir datos del backend, los identificadores llegan en formato `id_entidad` (por ejemplo `id_school`, `id_classroom`, `id_student`) — se respeta ese nombre tal cual llega de la API, sin renombrar a `entidadId` ni camelCase en la capa de datos, salvo que se defina una capa de mapeo explícita.
- Nombres de componentes en inglés y PascalCase (`AttendanceView`, `StudentProfile`, `AnnouncementModal`), consistentes con las entidades del backend.
